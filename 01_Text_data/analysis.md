# SentencePiece 감성 분류 프로젝트 실험 기록

## 1. 무엇을 풀었는가

NSMC 영화리뷰 본문으로 작성자의 긍정·부정을 분류했다. 영화 영상이나 영화 자체의 감정을 추론하는 프로젝트는 아니다. 같은 리뷰라도 토큰화 방식과 사전 크기가 다르면 입력 표현과 분류 결과가 어떻게 바뀌는지 비교했다.

SentencePiece 학습과 분류 모델 학습은 별개다. 전자는 라벨 없이 학습용 본문에서 조각 사전을 만들고, 후자는 토큰 ID와 긍정·부정 정답을 이용해 Embedding·LSTM·분류층의 값을 학습한다.

## 2. 실제 LMS 루브릭과 참고 관례

사용자가 LMS 화면으로 제공한 이번 프로젝트의 기준은 세 가지다.

1. 코퍼스 분석·전처리·SentencePiece 적용·토크나이저 구현과 동작을 빠짐없이 진행한다.
2. SentencePiece 토크나이저가 Text Classifier와 결합해 수렴하고 test accuracy 80% 이상을 확인한다.
3. 다른 토크나이저 또는 SentencePiece의 다른 옵션과 체계적으로 비교한다.

README·src·results·KPT·PRT 등은 사용자가 이전 CV 수업의 경험을 가져와 채택한 정리 방식이다. 그것을 이번 NLP의 추가 공식 채점 규정으로 확정하지 않는다. 원본 Step 4의 MeCab 비교, model_type·vocab_size 변경도 수행했다. FastText는 원본에서 선택적인 확장으로 안내되어 이번에 수행하지 않았다.

사용자는 최종 제출 형식은 GitHub URL이나 ZIP 등 본인이 선택한다고 명시했다. 제출 마감·지각 규정·특정 URL 형식을 임의로 추가하지 않는다.

원본: [NSMC](https://github.com/e9t/nsmc)의 ratings_train.txt와 ratings_test.txt.

157과 1,451은 각각 본문의 종류 수와 그 본문이 반복 등장한 행 수이므로 다르다. 학습 분할은 random_state=42, test_size=0.2, stratify=label이다. 사용자는 random_state가 같은 분할을 재현하고 stratify가 라벨 비율을 유지한다고 직접 설명했다.

감정 표현인 ㅋㅋ·ㅠㅠ·문장부호를 일괄 삭제하지 않았다. 학습용은 중복·라벨 충돌을 정리했고 테스트는 본문 결측·공백만 제외해 원래 구성을 유지했다. 문장 변환 규칙을 동일하게 적용하는 것과 평가 대상 행을 선별하는 것을 구별했다.

SentencePiece와 MeCab ID 사전은 학습용 본문만 이용했다. 검증·테스트를 사전 학습에 넣지 않았다. 테스트에서 겹친 1,147행은 전체 성능에는 포함하고, 그 행을 제외한 보조 성능을 함께 기록했다. 본문이 달라도 근접 중복이나 의미가 비슷한 리뷰는 있을 수 있다.

## 4. SentencePiece와 패딩에서 확인한 것

기존 뉴스 예제의 토크나이저는 사전 8,000개, UNK=0, PAD=-1이었다. PAD=-1은 전용 토큰을 사용하지 않는다는 뜻이다. 원본 함수의 padding_value=0을 그대로 쓰면 UNK와 PAD가 같아진다.

프로젝트에서는 UNK=0, PAD=1, BOS·EOS 비활성으로 학습했다. Python ID 리스트를 torch.long 텐서로 변환한 뒤 pad_sequence에 넣도록 고쳤다. .vocab 파일 이름을 고정해 읽는 대신 현재 SentencePiece 객체에서 토큰과 ID 대응표를 얻었다.

사용자는 “한 파일에 한 리뷰인가”라고 질문했고, 실제로는 파일 하나의 한 줄에 리뷰 하나를 저장한다고 확인했다. 학습용 파일은 116,820줄이었다.

첫 예문은 `이 영화 진짜 재밌어요ㅋㅋ`였다. unigram 8,000은 `▁이 / ▁영화 / ▁진짜 / ▁재밌어요 / ᄏᄏ`로 나눴고 ID는 `[27, 6, 31, 743, 137]`이었다. ▁는 공백 경계 표시이며 첫 토큰에도 붙을 수 있다. 기본 정규화로 ㅋㅋ가 ᄏᄏ로 바뀌어 원문과 복원 문자열의 유니코드 표현이 완전히 같지는 않았다.

## 5. 동적 패딩과 데이터셋

사용자는 전체 데이터의 가장 긴 리뷰가 아니라 배치 안의 최장 리뷰에 맞추는 아이디어를 직접 정리했다. 실제 검증 배치는 `[64,57]`이었고 첫 리뷰의 실길이는 19여서 뒤에 PAD 38개가 채워졌다.

Dataset은 리뷰 ID와 라벨 한 쌍을 반환하고, DataLoader는 64개씩 모으며, collate_batch는 그 배치에서만 패딩한다. 패딩 전 lengths를 함께 보관해 pack_padded_sequence로 LSTM이 뒤의 PAD를 처리하지 않도록 했다. padding_idx=1은 Embedding의 PAD 행을 학습에서 제외하는 역할이며, LSTM의 PAD 처리를 생략하는 것과 역할이 다르다.

## 6. 모델과 학습 조건

공통 구조: Embedding 128차원 → 단방향 1층 LSTM hidden_size=128 → Linear(128,2).

| 조건 | 설정 |
|---|---|
| batch size | 64 |
| model / shuffle seed | 42 |
| optimizer | Adam, learning rate 0.001 |
| loss | CrossEntropyLoss |
| gradient clipping | max_norm=1.0 |
| 최대 epoch | 10 |
| checkpoint 선택 | 검증 loss 최저 |
| 분할·평가 데이터 | 모든 실험에서 동일 |
| 토큰 길이 제한 | 첫 실험부터 미적용, 배치 동적 패딩 |
| dropout·weight decay·early stopping | 이번 코드에 추가하지 않음 |

사용자는 초기 점수 `[0.0304,0.0027]`의 합이 왜 1이 아닌지 물었다. 이는 확률 이전의 logits이고 Softmax 후 약 `[0.5069,0.4931]`이 된다. 학습에서는 CrossEntropyLoss에 logits를 그대로 전달한다.

`zero_grad`는 이전 기울기를 비우고, backward는 현재 loss의 기울기를 계산하며, optimizer.step이 파라미터를 바꾼다. 검증은 eval과 no_grad로 평가만 수행한다. “최적 모델 저장”은 실행 시간이 길다는 뜻이 아니라 이전보다 검증 loss가 낮아졌다는 뜻임을 구별했다.

## 7. 예상과 실제 관찰

| 실험 전 사용자 예상·질문 | 실제 결과와 해석 |
|---|---|
| train loss는 줄고 validation도 초기에는 줄지만 double descent가 나타날 수도 있다 | 네 실험 모두 후반 검증 loss가 증가했다. 10 epoch 범위에서 두 번째 하강은 관찰되지 않았다 |
| unigram이 확률을 이용하니 분류에 유리할 수 있다 | 확률은 토큰 분할의 확률이지 감성 확률이 아니다. 테스트는 unigram이 근소하게 높았지만 검증은 BPE가 근소하게 높았다. 일반적 우위나 원인으로 확정하지 않았다 |
| 사전이 작으면 파라미터가 적으니 빨라질 수 있다 | 평균 토큰 수가 증가해 LSTM이 더 많이 읽었다. 4,000개 실험의 epoch 시간은 평균 23.07초로 8,000개 20.10초보다 길었다. Colab 변동과 최초 환경 차이 등도 있어 인과를 확정하지 않았다 |
| MeCab은 UNK가 많은데 성능이 나올까 | 검증 86.50%, 테스트 86.13%로 이번 설정에서 가장 높았다. 낮은 UNK가 높은 정확도를 자동 보장하지 않았다 |

예측 문장은 사용자 생각을 바탕으로 다듬었고 실제 관찰과 분리했다. 최종 결과를 본 뒤 처음부터 예상했던 것처럼 다시 쓰지 않았다.

## 8. 네 실험 결과

| 토큰화 | 사전 | 평균 학습 토큰 수 | 선택 epoch | 검증 loss | 검증 정확도 | 테스트 정확도 | 비중복 테스트 |
|---|---:|---:|---:|---:|---:|---:|---:|
| unigram | 8,000 | 17.357 | 2 | 0.3401 | 85.11% | 84.88% | 84.68% |
| BPE | 8,000 | 17.021 | 2 | 0.3402 | 85.13% | 84.67% | 84.48% |
| unigram | 4,000 | 20.250 | 3 | 0.3459 | 84.93% | 84.70% | 84.49% |
| MeCab | 8,000 | 18.772 | 3 | 0.3155 | 86.50% | 86.13% | 86.02% |

위 표는 반올림한 표시값이다. 원래 정밀도의 수치는 [CSV](results/tokenizer_comparison.csv)에 보관했다. 네 실험 모두 저장된 checkpoint로 복원한 결과이며 마지막 epoch의 파라미터로 평가한 값이 아니다.

사전 8,000개 모델의 파라미터는 1,156,354개이고 4,000개는 644,354개다. Embedding에서 4,000×128=512,000개가 줄어든다. 문장이 길어져도 LSTM은 각 위치에서 같은 파라미터를 재사용하므로 파라미터가 토큰 수만큼 추가되지는 않는다.

## 9. MeCab UNK를 읽는 법

| 통계 | unigram 학습 | MeCab 학습 | unigram 검증 | MeCab 검증 |
|---|---:|---:|---:|---:|
| 평균 토큰 수 | 17.357 | 18.772 | 17.368 | 18.698 |
| 95% 길이 | 52 | 56 | 52 | 55 |
| 최대 길이 | 132 | 116 | 133 | 96 |
| UNK 토큰 비율 | 0.094% | 4.501% | 0.110% | 4.771% |
| UNK 포함 리뷰 비율 | 1.453% | 44.920% | 1.722% | 46.454% |

MeCab 학습용에서 찾은 형태소는 48,825종이지만 자주 나온 7,998종과 UNK·PAD만 등록했다. 이 UNK는 MeCab의 분석 실패율이 아니라 우리가 만든 제한된 사전에 없는 토큰의 비율이다.

사용자는 통계 함수의 코드를 다시 질문했다. 예시 `[[5,0,8],[3,4]]`에서 전체 토큰은 5개, UNK는 1개라 20%이고, 리뷰 2개 중 1개가 UNK를 포함하므로 50%임을 구분했다. 패딩 전 목록에서 센 통계라 PAD가 분모를 부풀리지 않았다.

## 10. 오분류와 문맥의 모호함

unigram 오답 7,559개, BPE 오답 7,666개, 공통 오답 5,244개였다. unigram만 정답 2,422개, BPE만 정답 2,315개, 공통 정답 40,016개로 합계 49,997개다. 두 모델의 예측이 다른 리뷰는 4,737개였다.

| 사례 | 라벨 / 두 모델 예측 | 관찰 |
|---|---|---|
| 눈에 보이는 반전이었지만 영화의 흡인력은 사라지지 않았다. | 긍정 / 둘 다 부정 | 상반된 평가와 부정 표현이 섞였다. 특정 단어가 원인인지는 출력만으로 모른다 |
| 소위 ㅈ문가라는 평점은 뭐냐? | 긍정 / 둘 다 부정 | 영화 평가인지 평가자 비판인지 대상을 구별해야 한다 |
| 애니는 일본이 갑인듯. | 긍정 / unigram 긍정, BPE 부정 | BPE 긍정 확률 0.499818로 경계에 가까웠다. 영화 국적·문맥에 따라 사람도 해석하기 어렵다고 사용자가 지적했다 |

사용자는 “영화를 평가하는 것인지 영화를 평가하는 평가자를 평가하는 것인지”와 문맥 부족을 직접 지적했다. 모델 한계만이 아니라 라벨의 모호함도 함께 고려해야 한다고 기록했다.

같은 예문의 분할을 비교했을 때 “애니는 일본이 갑인듯.”은 두 토크나이저의 조각이 완전히 같았지만 예측은 달랐다. ID와 학습된 파라미터가 다르므로 개별 리뷰의 분할만으로 차이를 설명할 수 없다. “갔다가”는 갔다+가 / 갔+다가, “였구나”는 통째 / 였+구나로 달랐다. 그 차이가 오답의 직접 원인이라는 주장은 하지 않았다.

## 11. 코드·기록에서 보완한 부분

| 원래 상태 | 보완 또는 기록 |
|---|---|
| Python 리스트를 pad_sequence에 전달 | torch.long 텐서로 변환 |
| UNK=0에 padding_value=0까지 사용 가능 | 전용 PAD=1 지정 |
| 고정 파일명의 .vocab 읽기 | 현재 processor에서 토큰↔ID 사전 생성 |
| 모든 문장을 전체 최장에 패딩할 수 있음 | 배치별 동적 패딩과 실제 lengths 사용 |
| 설명 문장이 코드 셀에 있음 | 사용자가 텍스트 셀로 수정, 최종 파일에서 확인 |
| “리뷰 하나당 파일 하나”라는 메모 | 원문을 보존하고 실제로는 한 파일·한 줄당 리뷰 하나라고 정정 추가 |
| “ID는 라벨”이라는 표현 | 감성 label과 혼동하지 않도록 사전 인덱스라고 보충 |
| 노트북 함수가 전역 optimizer·device를 참조 | src 사본에서는 인자로 명시해 모듈 단독 사용이 가능하도록 정리. 기존 실행 셀·결과는 변경하지 않음 |

새로 추가한 import 셀·요약과 src 정리는 새 전체 학습 결과가 아니다. 원본 실험은 Colab에서 수행했고, 정리 과정의 로컬 검증은 작은 CPU 데이터로만 한다. 전체 새 런타임·MeCab 설치부터의 재실행은 미검증이다.

## 13. 결과 해석의 한계와 다음 실험

- 한 시드·한 번씩 실행했다. 근소한 차이에 통계적 유의성을 부여하지 않는다.
- model_type·vocab_size 변경 외에도 사전 ID와 학습 경로가 달라진다. vocab_size 변경은 파라미터 수와 초기화 난수 배치도 바꿀 수 있다.
- MeCab과 SentencePiece는 분할·정규화·사전 구성의 묶음을 비교했다. 동일 정규화로 통제한 결과가 아니다.
- 학습·검증과 테스트의 정확히 같은 본문만 제외했다. 근접 중복·데이터 출처별 독립성까지 보장하지 않는다.
- 실험마다 테스트 점수를 열람했다. 선택 epoch는 검증 loss로 골랐지만 완전히 봉인된 최종 평가라고 표현하지 않는다.
- 시간은 Colab 부하·실행 순서 등의 영향을 받는다. 기록된 epoch 시간은 토크나이저 학습 시간을 포함하지 않으며 엄밀한 속도 benchmark가 아니다.
- 추가 실험 제안: 여러 시드로 반복, 정규화 통일, MeCab 사전 크기 확장과 UNK 변화, 같은 표현에서 분류기 변경, validation 기반 early stopping·정규화 비교. 아직 수행하지 않았다.
