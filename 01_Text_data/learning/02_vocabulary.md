# 노드 2: 멋진 단어사전 만들기

출처는 `2 멋진 단어사전 만들기 [프로젝트].ipynb`의 학습 부분과 대화다. 아래 셀 번호는 사용자가 마지막으로 내려받은 전체 노트북의 JSON cells 배열 1기준이다. 이 수치는 프로젝트의 NSMC 리뷰 통계와 다르다.

## 1. 문장 길이 분포를 먼저 본 이유

사용자는 histogram의 X축이 문장 길이라면 Y축은 무엇인지 물었다. X축은 해당 코드의 `len(sentence)`, 즉 **문자 수**였고, Y축은 그 길이에 해당하는 문장의 수였다. 토큰 수를 잰 그래프가 아니다.

노트북 저장 출력의 뉴스 말뭉치 통계는 다음과 같다.

| 단계 | 문장 수 | 최소 문자 수 | 최대 문자 수 | 평균 문자 수 |
|---|---:|---:|---:|---:|
| 원본 | 94,123 | 1 | 377 | 약 60 |
| 중복 제거 후 | 77,591 | 1 | 377 | 약 64 |
| 길이 필터 후 | 76,908 |  |  |  |

근거: 셀 14·16·24·32. 평균은 원래 출력이 정수로 표시한 값이다.

사용자는 길이 1인 항목이 공백처럼 보인다고 했고, 저장된 출력 셀 18에는 `’`가 있었다. 관찰한 화면과 파일 출력의 차이를 남기며 “모두 공백이었다”고 확정하지 않았다.

## 2. 분포의 스파이크와 중복

길이 11·19·21 부근에 문장이 유독 많았다. 사용자는 실제 문장을 확인한 뒤 중복 처리가 안 되어 있었다고 짚었다. 셀 20에 해당 길이가 표시되고 셀 22에는 같은 문장이 반복된 사례가 남아 있다.

단순히 그래프 봉우리를 보고 오류라고 단정하지 않고 실제 항목을 확인했다. `list(set(raw))`는 중복을 없애지만 순서를 바꿀 수 있다. 한국어·영어 번역처럼 쌍인 데이터의 두 쪽에 독립 적용하면 정렬 관계를 훼손할 수 있다.

또한 원래 분포 코드에서 길이와 배열 인덱스가 한 칸 차이 나는 부분을 주의했다. 그래프의 x값과 실제 문장 길이를 동일시하기 전에 인덱스 사용을 확인해야 한다.

## 3. 길이 필터와 패딩

`10 <= len(sentence) < 150` 조건이 어떻게 문장을 통과시키는지 사용자가 처음에는 어려워했지만, 조건에 따라 리스트에 넣는 코드를 보고 이해했다고 말했다.

아주 긴 문장이 섞이면 패딩 때문에 빈칸이 늘 수 있다. 다만 이 뉴스 예제의 필터 기준은 **문자 수**이며, 이후 모델에 입력할 토큰 길이와 같지는 않다. 프로젝트에서는 학습 데이터의 실제 토큰 길이를 따로 측정하고 전체 최장이 132였으므로 첫 실험에서 자르지 않았다.

## 4. 공백 토큰화와 형태소 토큰화

근거: 공백 사전 셀 34, MeCab 사전 셀 41.

| 뉴스 말뭉치 토큰화 | 사전 크기 |
|---|---:|
| 공백 기준 | 238,305 |
| MeCab | 53,642 |

한국어 어미·조사가 붙은 형태를 공백 단위로 모두 별도 항목으로 두면 사전이 커질 수 있다. 형태소 분석은 작은 단위를 공유할 수 있다.

이 수치가 사전이 작을수록 항상 더 빠르고 정확하다는 증거는 아니다. 사용자는 프로젝트에서 파라미터 수와 토큰열 길이가 서로 다른 방향으로 바뀔 수 있다는 점까지 다시 확인했다.

## 5. 노드의 비교 질문을 따라간 과정

셀 43~45의 질문에 대해 사용자는 다음 이유를 제시했다.

- 같은 모델 원리라도 한국어 데이터로 학습한 모델이 한국어 task에 유리할 수 있다.
- 형태소 분석기는 한국어의 구조를 이용해 단위를 나눈다는 점이 다르다.
- SentencePiece는 처음 보는 단어를 작은 조각으로 표현해 OOV에 대응할 수 있다.

보충 설명에서는 훈련 데이터의 언어·도메인, 사전과 모델 학습의 차이를 함께 고려했다. 형태소 분석기는 모든 언어에 같은 도구를 그대로 적용하기 어렵고 사전 유지가 필요하다. 반대로 subword의 UNK 감소만으로 모든 과제의 성능을 보장하지는 않는다. 프로젝트 MeCab 결과가 그 점을 보여 주었다.

## 6. 디코딩이 실제로 되돌리는 것

셀 46~50에서 `sequences_to_texts()` 또는 `index_word`를 이용해 ID를 토큰으로 되돌렸다. **ID를 만들 때 쓴 바로 그 사전**이 필요하다.

PAD로 쓴 0은 건너뛰어야 한다. 형태소를 공백으로 연결하면 토큰 목록은 읽을 수 있지만, 원문의 정확한 띄어쓰기까지 복구되는 것은 아니다. SentencePiece는 경계 정보를 보존하지만 정규화 때문에 원문 문자 표현이 달라질 수 있다.

## 7. SentencePiece 프로젝트로 이어진 단계

셀 51부터 프로젝트 안내가 시작된다. 앞의 뉴스 말뭉치로 SentencePiece를 만드는 예제와, Step 4에서 NSMC 감성 분류를 수행하는 실험을 구별했다.

사용자는 전체 프로젝트를 맡기면 나중에 각 셀을 다시 질문하게 된다고 말했다. 이에 따라 기존 Colab 노트북에서 셀의 목적·입출력과 결과를 함께 확인하는 방식으로 진행했다. 새 Colab 노트북을 처음부터 만들지 않았다.

초기 상태 확인 결과 PyTorch 2.11.0+cu130, SentencePiece 0.2.2, Tesla T4였다. 기존 뉴스용 사전은 8,000개, UNK=0, PAD=-1이었다. PAD=-1은 패딩 토큰이 비활성화됐다는 뜻이지 입력에 -1을 채운다는 뜻이 아니다.

원본 `sp_tokenize()`는 Python ID 리스트를 바로 `pad_sequence`에 넘기고 padding_value=0을 고정했다. 프로젝트에서는 정수 텐서 변환과 PAD 전용 ID=1을 적용했다. 이 수정은 로컬 원본 강의 파일을 덮어쓴 것이 아니라 프로젝트 코드에서 보완한 것이다.

## 8. 남겨 둔 개념 연결

전처리 → 토큰화 → ID → Embedding → LSTM 감성 분류로 이어졌다. 토큰화는 표현 단위를 고르고, ID는 구별 번호를 부여하며, Embedding과 분류 모델이 감성 정답을 이용해 값을 학습한다.

프로젝트의 상세 실험은 [analysis.md](../analysis.md), 실행 결과는 [프로젝트 노트북](../notebooks/sentencepiece_sentiment.ipynb)에 연결했다.
