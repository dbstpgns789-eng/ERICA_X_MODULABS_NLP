# 노드 1: 텍스트 데이터 다루기

출처는 ZIP의 `1 텍스트 데이터 다루기.ipynb`와 학습 대화다. 셀 번호는 Markdown을 포함한 JSON cells 배열의 1기준 번호다. 사용자 설명은 대화에서 확인된 범위이고, 보충 설명 전체를 이해 검증으로 처리하지 않는다.

## 1. 전처리: 무엇을 지워야 하는가

원본 위치: 셀 17~31. 문장부호 21, 대소문자 24, 특수문자·하이픈 28.

사용자는 영화리뷰의 `ㅋㅋㅋ`, `ㅠㅠ`, 문장부호가 감정을 표현하거나 강조할 수 있으므로 전부 삭제하면 안 된다고 말했다. 이에 따라 전처리를 “노이즈를 최대한 지우기”가 아니라 **현재 과제에 필요한 정보를 보존하며 입력을 정리하기**로 이해했다.

하이픈을 빈 문자열로 바꾸면 `ten-year-old`가 `tenyearold`로 붙는 문제를 지적했다. 삭제와 공백 치환은 결과가 다르며, 어떤 경계를 보존할지 먼저 결정해야 한다. 소문자화는 `Apple`과 `apple` 같은 표기를 합칠 수 있지만, 대문자 정보가 유용한 과제에서는 무조건 적용할 규칙이 아니다.

프로젝트에서는 감정 표현을 임의로 제거하지 않았다. 본문 결측·공백 행과 학습 데이터의 중복·라벨 충돌을 정리했다.

## 2. 희소 표현과 분산 표현

원본 위치: 셀 32~37.

사용자는 성별·나이 등 사람이 정한 속성의 예시를 따라가면서, 속성을 계속 추가하는 것이 희소 표현인지 질문했다. 이후 **차원이 커도 0이 대부분이고 0이 아닌 값이 적으면 sparse**라고 직접 설명했다. 고차원이라는 사실만으로 sparse인 것은 아니다.

학습 중 구별한 개념은 다음과 같다.

| 구분 | 뜻 | 주의점 |
|---|---|---|
| 희소 표현 | 대부분의 성분이 0인 벡터 | 차원 수가 많다는 것과 동일하지 않다 |
| 분산 표현 | 정보가 여러 성분에 걸쳐 표현됨 | “어느 성분도 해석 불가능”이라는 뜻은 아니다 |
| one-hot | 한 위치만 1이고 나머지는 0 | 위치가 단어를 식별하지만 단어의 의미 속성을 직접 설명하지는 않는다 |
| dense embedding | 상대적으로 적은 차원의 학습된 실수 벡터 | 각 축에 사람이 정한 속성 이름이 붙는 것이 기본은 아니다 |

사용자는 “희소는 단어의 뜻을 정확히 알 수 있고 분산은 뜻이 흩어진 것인가”라고 물었다. 보충 설명에서는 one-hot의 어떤 칸이 어느 단어인지 알 수 있다는 것과 그 단어의 의미를 표현한다는 것을 구별했다. **희소성·해석 가능성·의미 표현은 서로 다른 성질**이다.

## 3. Embedding Layer와 차원의 의미

사용자는 처음부터 등장한 Embedding Layer를 알아야 뒤 설명을 이해할 수 있다고 짚었다. Embedding은 **토큰 ID를 학습 가능한 벡터에 연결하는 표**로 설명했다. 행은 토큰이고 열은 벡터의 성분이다.

사람이 `[성별, 나이, 국적]` 같은 열 이름을 미리 정해야 하는지 질문했다. 일반적인 학습형 Embedding에서는 사람이 차원 수를 정하지만, 성분 값은 학습 목표의 오차를 줄이도록 조정된다. 특정 열이 성별이나 과일 여부를 뜻하도록 지정하지 않는다.

사용자는 사과와 바나나의 첫 칸이 비슷하다고 “그 칸은 과일 여부”라고 해석하면 가설을 사실처럼 말하는 것이라고 지적했다. 단어 집단이나 probe 등으로 관련성을 조사할 수는 있지만, 비슷한 성분 하나만으로 의미 이름을 확정할 수 없다. 차원이 커서 사람이 전혀 감을 못 잡는다는 설명도 과도하다.

또한 “단어가 따로 끊겨 있어서”보다 **동일 단어에 같은 벡터를 주는 정적 표현이 문맥별 차이를 표현하지 못한다는 점**을 질문했다. 정적 Embedding과 문맥을 읽는 후속 모델을 구별했다. 정적 Embedding을 쓴다고 전체 분류 모델이 문맥을 전혀 못 읽는 것은 아니다. 프로젝트의 LSTM이 토큰 순서를 처리한다.

## 4. 토큰화가 왜 필요한가

원본 위치: 셀 38~52.

사용자는 “중요한 전처리이고 성능을 향상한다”는 답이 왜 필요한지를 설명하지 못한다고 비판했다. 논의한 핵심은 **문자열을 모델이 다룰 수 있는 반복 가능한 단위로 정하고, 그 단위를 ID와 벡터에 연결하기 위해서**라는 것이다.

문장 전체를 언제나 하나의 ID로 처리하면 처음 보는 문장이 매번 새로운 항목이 된다. 반대로 단위를 지나치게 작게 잡으면 길이가 늘고 더 긴 조합을 학습해야 한다. 공백·형태소·subword는 무엇을 공유하고 무엇을 구별할지에 대한 서로 다른 선택이다. 토큰화가 의미 이해나 성능 향상을 자동 보장하지 않는다.

사용자는 `트와이스`를 하나의 토큰으로 찾았다고 그 시스템이 걸그룹을 알고 나눈 것은 아니라고 직접 설명했다. **분할과 의미 학습을 구별**한 부분이다.

## 5. OOV와 BPE

원본 위치: OOV 셀 52, BPE 셀 54~58.

사용자는 유한한 단어 사전에서 처음 보는 단어 문제가 발생한다고 짚었다. BPE에 대해서는 **UNK 하나가 될 단어를, 알려진 조각들의 ID 조합으로 표현하게 하는 것**이라고 직접 정리했다.

BPE는 작은 기호에서 시작해 자주 인접한 쌍을 반복해서 병합한다. 예를 들어 `lowest` 전체가 없어도 `low`와 `est`가 있으면 두 토큰으로 표현할 수 있다. 이는 표현할 수 있게 됐다는 뜻이지, 접미사의 의미를 반드시 이해했다는 뜻은 아니다.

UNK가 완전히 사라진다고 일반화하지 않았다. 기본 문자 집합에 없는 문자 등은 여전히 문제가 될 수 있고, 프로젝트에서 실제 UNK 비율을 측정했다.

## 6. 조각을 다시 문장으로 되돌리기와 WPM

원본 위치: WPM 셀 59~61.

사용자는 `[i, am, a, b, o, y, ...]` 같은 조각을 모두 붙이면 단어 경계가 사라지는 문제를 질문했다. 토큰 조각 외에 **공백·단어 경계를 복원할 정보**가 필요하다는 흐름으로 설명했다.

경계 표시는 구현마다 다르다. 어떤 WordPiece 구현은 이어지는 조각에 `##`를 붙이고, SentencePiece는 공백을 `▁`로 표현한다. 특정 표시가 모든 WPM 구현의 보편적 규칙이라고 단정하지 않았다.

사용자는 공백 처리의 목적은 이해했지만 likelihood 기준은 이해가 충분하지 않아, 노드 안내에 맞춰 깊게 계산하지 않고 soynlp로 이동했다. WPM과 unigram의 확률 설명을 같은 알고리즘으로 합쳐 기록하지 않는다.

## 7. soynlp에서 의미 학습으로

원본 위치: 셀 62~64.

soynlp가 반복 패턴·통계적 결합을 이용해 단어 후보를 찾는 것과, 대상의 실제 의미를 안다는 것은 다르다. 사용자의 `트와이스` 설명을 이 경계에 연결했다.

사용자는 노드에서 설명 대신 외부 학습자료 링크로 이어지는 부분을 지적했고, 링크만 전달하기보다 연결된 Word2Vec 설명과 그림을 함께 따라갔다.

## 8. Word2Vec: one-hot과 행렬

원본 위치: 셀 65~68. 추가 학습자료: [Word2Vec 설명](https://wikidocs.net/22660), [원 논문](https://arxiv.org/abs/1301.3781).

사용자는 “주변 단어로 중심 단어를 맞히는 task를 하면서 의미를 배우는 것”으로 연결했다. one-hot과 행렬의 곱이 lookup과 어떻게 같은지 질문했다.

사전 크기가 V, 벡터 크기가 D이면 Embedding 행렬 W의 크기는 V×D다. i번째 one-hot 벡터 e_i와 곱하면 `e_i W = W[i]`가 되어 해당 행을 선택한다. lookup이라는 구현과 one-hot 행렬곱이라는 설명이 같은 선택 연산을 나타낸다.

| 방식 | 입력 | 학습 중 맞힐 대상 |
|---|---|---|
| CBOW | 주변 단어들 | 중심 단어 |
| Skip-gram | 중심 단어 | 주변 단어들 |

CBOW의 주변 벡터 평균을 보고 사용자는 “중심 단어에 더 큰 영향을 주는 단어도 있을 텐데 평균내면 뭉개진다”고 지적했다. 동일 가중 평균은 문맥 내 기여도와 순서에 대한 정보를 제한한다. 이 직관은 가중치를 다르게 주는 방법으로 연결되지만, Word2Vec이 곧 Attention이라는 뜻은 아니다.

사용자는 확률과 정답의 차이를 CE로 계산하고 그 오차를 줄이도록 행렬 값을 고친다고 직접 설명했다. 이것을 프로젝트의 `loss.backward()`와 `optimizer.step()`으로 연결했다.

## 9. Skip-gram이 항상 더 좋은가

사용자는 주변 여러 단어를 보면 중심 하나를 맞히는 것이 더 쉬울 것 같아 Skip-gram 성능이 좋다는 설명을 의외로 받아들였다. 여기서 **훈련 과제의 쉬움과 학습된 벡터의 평가 성능은 다르다**는 점을 구별했다.

원 논문 Table 3의 같은 640차원 조건에서는 semantic analogy가 CBOW 24%·Skip-gram 55%, syntactic analogy가 CBOW 64%·Skip-gram 59%였다. 따라서 “성능이 좋다”는 말에는 평가 과제와 조건이 필요하며, 모든 지표에서 Skip-gram이 우수하다고 말할 수 없다.

사용자는 projection 층을 가진 shallow network라고 지적했고, 가중 문맥 처리가 Attention과 연결될 것 같다는 아이디어를 말했다. 이 부분은 사용자의 학습 직관이며 역사적 발전 관계를 검증한 주장으로 기록하지 않는다.

## 다시 확인할 부분

- 희소성, 분산 표현, 해석 가능성은 각각 어떤 질문에 답하는가.
- 같은 ID에 대응하는 정적 벡터와 문맥을 읽은 LSTM 상태는 어떻게 다른가.
- BPE의 표현 가능성과 의미 이해를 왜 구별하는가.
- WPM의 likelihood 세부 계산은 깊게 다루지 않았다.
- FastText·ELMo는 원본 노드에 있지만 이번 대화에서 끝까지 학습했다고 처리하지 않는다.
